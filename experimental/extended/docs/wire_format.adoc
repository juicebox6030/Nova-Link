= NOVA-LINK Wire Formats (as implemented)
:toc:

This document applies only to `experimental/extended/`; paths below are relative
to that directory. Its API and CRC-8 link framing differ from the root SDK.

This is the byte-level reference for what the portable core in `src/`
actually puts on the air and on the host <-> radio link. Where it differs
from the root SDK or earlier design notes, the formats here describe only
this prototype and do not replace the root protocol decisions. The C headers named in each section are the
authoritative source; `tools/novalink/` implements the same formats in
Python, and `tests/vectors/` holds generated byte vectors that both
implementations are tested against.

All multi-byte integers are little-endian. Times are microseconds.

== Air: DataFragment

Header: `include/nova_link/nl_fragment.h`

[cols="1,1,4"]
|===
|Offset |Size |Field

|0 |1 |Header byte: `originID << 5 \| zoneID << 2 \| flags`
|1 |1 |seqNum (per origin and zone, wraps at 256)
|2 |0..100 |Payload
|===

* originID (3 bits): sender, 0..7. Receivers ignore their own origin.
* zoneID (3 bits): 0 is the metadata zone, 1..7 carry plugin data.
* flags (2 bits):
** `0x02` BURST: more fragments follow; the receiver extends its listen
   slot on this zone by `burst_extend_us`.
** `0x01` MGMT_LISTEN: the sender has metadata pending; receivers bring
   zone 0 into their rotation for `mgmt_hold_us`.

The maximum fragment is 102 bytes. Duplicates (repeats) are discarded by
the stream tracker on (origin, zone, seqNum). An entry older than
`tracker_stale_us` is forgotten, so a rebooted sender whose sequence numbers
restart is accepted again.

== Air: zone 0 metadata records

Header: `include/nova_link/nl_meta.h`

A zone 0 payload is a sequence of TLV records, packed "as they fit" into
one fragment. A record never spans fragments, so a value is at most 98
bytes.

  [type u8][len u8][value: len bytes] [type][len][value] ...

Receivers skip types they do not know, so new types can be added without
breaking older firmware. Types 0x80..0xFF are free for vendor use.

[cols="1,2,5"]
|===
|Type |Name |Value

|0x01 |DEVICE_ANNOUNCE
|`proto_version u8, fw_major u8, fw_minor u8, fw_patch u8, name[0..24]`
(UTF-8, not NUL-terminated)

|0x02 |CLAIM_ANNOUNCE
|Full snapshot of the sender's zone claims, 4 bytes each:
`zone u8, mode u8, plugin_type u16`. Modes: 1 shared, 2 exclusive,
3 read-only.

|0x03 |PLUGIN_DATA
|`plugin_type u16, data...`

|0x04 |CONGESTION
|`zone_mask u8, dropped u16`

|0x05 |DEBUG_TEXT
|UTF-8 text, not NUL-terminated

|0x06 |PEERS
|`origin_mask u8`: bit _i_ set means the sender currently considers origin
_i_ a live peer (its own bit is never set). Sent immediately after
DEVICE_ANNOUNCE so both share a fragment. A device whose bit is clear has
not been heard by the sender and answers with its own announcements after
a short random delay (see <<discovery>>).
|===

Example: device 0 (no name set) announcing that it knows origins 2, 3 and
6, as one fragment on zone 0 with seqNum 9:

  00 09 | 01 04 01 00 01 00 | 06 01 4c
        DEVICE_ANNOUNCE (v1, fw 0.1.0, no name)   PEERS {2, 3, 6}

`tools/nl_decode.py` prints this kind of breakdown for any captured hex.

[[discovery]]
=== Discovery and announcement timing

Implemented in `src/nl_host.c`. Defaults are in `config/nova_link.ini`.

* Every `announce_interval_us` (2 s) the host queues DEVICE_ANNOUNCE,
  PEERS and CLAIM_ANNOUNCE. Each period is shortened by a random
  0..`announce_jitter_us` (250 ms).
* The first announcement after boot is delayed by a random
  0..`announce_boot_spread_us` (100 ms), so devices powered up together do
  not all transmit at once.
* `announce_ramp_steps` (3) makes the first periods shorter: interval/8,
  interval/4, interval/2, then the full interval.
* A device answers early, after a random 0..min(`announce_jitter_us`,
  `mgmt_hold_us`/2), when it hears an announcement from a peer it did not
  know, or a PEERS record that lacks its own bit. Without the PEERS check,
  a device that missed one announcement could wait a full interval
  (measured outliers of about 2 s in simulation; with it, the worst case
  over 64 seed/config runs was 357 ms).

== Link: frame format

Header: `include/nova_link/nl_link.h`

Every message between host and radio, on SPI or UART, is one frame:

  +------+-----+-----+-----------+------+
  | 0xAA | CMD | LEN | DATA[LEN] | CRC8 |
  +------+-----+-----+-----------+------+

* CRC-8/SMBUS (poly 0x07, init 0x00) over CMD, LEN and DATA.
* CMD 0x00 and 0xFF are never valid. An idle line reads as one of them, and
  with a zero-initialised CRC the bytes `AA 00 00 00` would otherwise form
  a valid-looking frame.
* Receivers skip filler bytes before SYNC, and skip candidate SYNC bytes
  that do not lead to a valid frame.

On SPI each request takes two transactions, because the radio (SPI slave)
can only clock out bytes it prepared before the transaction started:

. The host sends the request frame. The radio parses it and prepares the
  response in its outbox.
. For commands that have a response, the host waits `turnaround_us`
  (default 50 µs), then clocks out filler zeros and reads the response
  frame.

PULL is never retried, because the radio dequeues the fragment when it
answers; a retry after a corrupted response would skip a fragment. PING
and STATUS are idempotent and are retried.

=== Commands

[cols="1,2,1,4"]
|===
|CMD |Name |Response |DATA

|0x01 |PING |0xD1 |none
|0x02 |PULL |0xD0 |none
|0x03 |PUSH |none |One DataFragment (2..102 bytes)
|0x04 |STATUS |0xD4 |none
|0x05 |ZONE_CONFIG |none |Zone plan, 72 bytes
|0x06 |RADIO_CONFIG |none |Radio parameters, 37 bytes
|0xD0 |FRAGMENT | |One received DataFragment; LEN 0 means none pending
|0xD1 |PONG | |`proto_version, fw_major, fw_minor, fw_patch` (4 bytes)
|0xD4 |STATUS | |Status block, 28 bytes
|===

The radio raises its INT_READY line while received fragments wait for a
PULL.

=== ZONE_CONFIG (72 bytes)

Eight 9-byte entries, zone 0 first:

[cols="1,1,4"]
|===
|Offset |Size |Field

|0 |1 |priority: rotation weight 1..8, 0 = not in rotation (zone 0 then
joins only while active)
|1 |4 |sub-GHz centre frequency, Hz (0 = none)
|5 |4 |2.4 GHz centre frequency, Hz (0 = none)
|===

A zone with no frequency for the selected band is never scheduled.

=== RADIO_CONFIG (37 bytes)

[cols="1,1,2,1,4"]
|===
|Offset |Size |Field |Default |Notes

|0 |1 |origin_id |0 |0..7; own echoes are ignored
|1 |1 |band |0 |0 sub-GHz, 1 2.4 GHz, 2 dual
|2 |1 |tx_policy |0 |0 immediate, 1 only in the zone's slot
|3 |1 |tx_repeats |3 |>= 1
|4 |4 |dwell_us |2000 |listen time per rotation slot
|8 |4 |burst_extend_us |4000 |extra dwell after hearing BURST
|12 |4 |mgmt_hold_us |250000 |zone 0 stays in rotation after MGMT_LISTEN
|16 |4 |repeat_interval_us |1500 |minimum gap between repeats
|20 |4 |tracker_stale_us |500000 |dedup entry expiry
|24 |4 |repeat_jitter_us |1000 |random extra 0..N per repeat gap
|28 |4 |discovery_interval_us |20000 |visit zone 0 at least this often (0 = only when pulled)
|32 |1 |mgmt_repeats |6 |transmissions per zone 0 fragment (0 = tx_repeats)
|33 |4 |cca_backoff_us |2000 |listen before talk; busy channel defers 1..N (0 = off)
|===

The radio rejects a block with the wrong length, origin_id > 7, an unknown
band or policy, or tx_repeats 0.

=== STATUS (28 bytes)

[cols="1,1,4"]
|===
|Offset |Size |Field

|0 |1 |proto_version (`NL_LINK_PROTOCOL_VERSION`)
|1 |1 |flags: 0x01 RX pending, 0x02 configured
|2 |1 |rx_queue_len
|3 |1 |tx_queue_len (all zones)
|4 |4 |rx_ok: new fragments accepted
|8 |4 |rx_dup: duplicates or stale fragments discarded
|12 |4 |rx_dropped: accepted, but the RX queue was full
|16 |4 |rx_ignored: malformed, own origin, or unsubscribed zone
|20 |4 |tx_sent: RF transmissions (each repeat counts)
|24 |4 |tx_dropped: evicted from a full TX queue
|===

Counters are free-running and wrap.

== Radio platform contract

Header: `include/nova_link/nl_radio.h`

The radio core never touches hardware. The CC1352R firmware runs this loop:

[source,c]
----
for (;;) {
    nl_radio_action_t act;
    nl_radio_next_action(&radio, now_us(), &act);
    switch (act.type) {
    case NL_ACT_TX:
        if (act.cca && rf_channel_busy(act.freq_hz)) {
            nl_radio_tx_busy(&radio, now_us());   /* retry later */
        } else {
            rf_transmit(act.freq_hz, act.data, act.len);
        }
        break;
    case NL_ACT_RX:
        /* listen on act.freq_hz until act.until; for each packet call
         * nl_radio_rx_packet(), then loop */
        break;
    case NL_ACT_IDLE:
        sleep_until(act.until);
        break;
    }
    gpio_set(INT_READY, nl_radio_int_ready(&radio));
}
----

After every SPI transaction the platform calls `nl_radio_spi_complete()`
with the received bytes, then preloads `nl_radio_outbox()` (padded with
zeros) for the next transaction.

Expectations the simulator showed to matter (see `simulation.adoc`):

* *Finish a packet in progress.* If a listen slot ends while a packet is
  being received, keep receiving until it completes. Aborting it dropped
  delivery from 98.6% to 69.3% in the 4-node simulation.
* *Wake on PUSH.* When a PUSH arrives during an RX or IDLE action, return
  to `nl_radio_next_action()` so the fragment can go out immediately.
  Waiting for the slot to end cost about 3.6 points of delivery.
* *Clear-channel check.* When `act.cca` is set, check the channel (on the
  CC13xx, `CMD_PROP_CS` or the RSSI threshold) before transmitting. If it
  is busy, call `nl_radio_tx_busy()` instead of transmitting. The core puts
  the fragment back, retries it after a random 1..`cca_backoff_us`, and
  after 8 deferrals in a row transmits anyway. After receiving a packet the
  core also holds off its own transmissions for a random
  0..`cca_backoff_us`. The exact busy threshold and check time on real
  hardware are not yet verified.
